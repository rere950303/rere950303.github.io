## 들어가며
- Milvus 2.6.22에서 **HNSW(dense) + BM25 하이브리드 검색**을 하려고 한다. 클러스터는 언어권별로 따로 둔다.
  - **KR 클러스터**: 한국어 위주, 일본어·영어가 일부 섞인다.
  - **JP 클러스터**: 일본어 위주, 한국어·영어가 일부 섞인다.
- 용도는 앱 검색이라 유저는 주로 **키워드**로 검색할 것으로 본다.
- 고민한 질문: **문서 언어를 감지해 `multi_analyzer_params`로 언어별 토크나이저를 쓰면, 토크나이저 하나로 통일할 때보다 실제로 나은가?** 애매한 쿼리는 여러 분석기로 **fan-out**해서 RRF로 합치는 것도 같이 검토했다.
- 공개 데이터셋으로 직접 벤치마크를 돌려 확인했다.

## 결론부터

| 질문 | 결론 |
|---|---|
| KR 클러스터에 multi analyzer가 필요한가? | **필요 없다.** 한국어 토크나이저(ko-dic) 하나로 섞여 들어오는 일본어·영어도 충분히 처리된다. |
| JP 클러스터에 multi analyzer가 필요한가? | **필요하다.** 섞여 들어오는 한국어 검색 품질이 크게 오르고, 일본어·영어 쪽 손해는 없다. |
| 애매한 쿼리를 fan-out해야 하나? | **하지 않는다.** 이득이 없고, RRF로 합치면 오히려 떨어진다. |
| dense + BM25 랭킹은 RRF가 최선인가? | **아니다.** 이 데이터에서는 RRF가 dense만 쓸 때보다도 나빴다. 정규화 후 가중합(dense 0.7)이 가장 좋았다. |
| 텍스트 정규화가 필요한가? | **넣자.** NFKC + `removepunct` / `asciifolding` / 영어 `stemmer`. 이 데이터에서는 효과가 작았지만 손해도 없었다. |

## 핵심 개념과 이유 정리

### 언어 지정 규칙: insert와 query에 똑같이 적용한다

| 텍스트 | 지정할 언어 | 이유 |
|---|---|---|
| 한글이 있음 (일본어·영어가 섞여 있어도) | `ko` | ipadic은 한글을 `비행장은`처럼 조사가 붙은 어절 단위로만 잘라 거의 매칭되지 않는다. ko-dic은 일본어·영어도 그럭저럭 자른다. 손해가 작은 쪽을 고른다. |
| 가나가 있음 (영어가 섞여 있어도) | `ja` | 가나는 일본어라는 확실한 신호다. ipadic은 영어도 `chatgpt / で / 画像`처럼 잘 자르지만, 영어 분석기는 일본어를 통째로 토큰 하나로 만든다. |
| 영어만 있음 | `en` | 어간 처리(`apps` → `app`)와 불용어 처리를 받는다. 기본 언어 분석기와의 차이는 작아서 어느 쪽이어도 큰 문제는 없다. |
| 한자만 있음 | 클러스터 기본 언어 (KR은 `ko`, JP는 `ja`) | 일본어인지 중국어인지 구분할 수 없다. 중국어 문서는 거의 없으니 클러스터의 주력 언어로 보낸다. KR 클러스터에서는 한자 키워드를 ko-dic으로 처리한 결과가 ipadic으로 보낸 것보다 좋았다(BM25 0.578 vs 0.545). |

- **insert와 query 규칙이 같아야 하는 이유**: BM25는 토큰이 정확히 일치해야 점수가 난다. 같은 문자열이라도 insert 때 분석기 A, query 때 분석기 B로 자르면 토큰이 달라져 매칭이 깨진다. 그래서 같은 감지 함수를 양쪽에 쓴다.
- **Milvus에서 지정하는 위치**
  - insert: `multi_analyzer_params`의 `by_field`로 지정한 필드(예: `lang`)에 언어 값을 넣는다.
  - query: 검색 파라미터에 `analyzer_name`으로 같은 값을 넘긴다.

### fan-out은 왜 효과가 없나
- fan-out은 insert 언어는 정해 두고, query 언어가 애매할 때 후보 분석기 2~3개로 각각 검색해서 합치는 방식이다.
- **이득이 나려면** 같은 문자열을 분석기마다 다르게 자르고, 정답 문서가 다른 분석기로 저장돼 있어야 한다. 실제로는 이런 경우가 거의 없다.
  - 영어 부분은 ko-dic, ipadic, english 모두 소문자 + 단어 단위로 똑같이 자른다. 그래서 어느 분석기로 검색해도 같은 토큰이 나오고, 같은 문서가 걸린다.
    - 예: 문서 `ChatGPTで画像生成できるアプリ`를 ja로 저장하면 토큰은 `chatgpt / で / 画像 / 生成 / できる / アプリ`다.
    - 쿼리 `ChatGPT`는 ja, en, ko 어느 분석기로 잘라도 `chatgpt`가 되어 이 문서와 매칭된다. ja와 en으로 fan-out하면 같은 결과를 두 번 받는 셈이다.
    - 예외는 어간 처리뿐이다(아래 `stemmer` 참고).
  - 한국어+일본어 혼합에서 ja로 검색하면 한글 부분이 매칭되지 않는다. 그래서 ko 하나로 검색하는 것보다 나아질 게 없다.
- **손해가 나는 이유**: 틀린 분석기로 자른 쿼리는 엉뚱한 문서와 한두 글자만 겹친다. 그런데 RRF는 점수를 보지 않고 순위만 본다. 그래서 그 노이즈 결과의 1등이 정상 결과의 1등과 같은 가산점을 받는다.
- 문서별로 BM25 점수가 높은 쪽만 남기는 방식으로 합치면, 노이즈는 점수가 낮아서 뒤로 밀린다. 그러면 손해는 사라지지만 이득도 없다. 쿼리 수만 늘어난다.

### min-max 정규화 가중합
- dense 점수(cosine)는 대략 0.3~0.9, BM25 점수는 0~수십이다. 범위가 달라서 그대로 더할 수 없다.
- **min-max 정규화**: 쿼리마다 각 결과 리스트 안에서 `(점수 − 최솟값) / (최댓값 − 최솟값)`으로 0~1로 맞춘다.
- 그다음 `0.7 × dense + 0.3 × BM25`로 더한다. 한쪽 리스트에 없는 문서는 그쪽 점수를 0으로 본다.
- 예: dense 점수가 0.40~0.80, BM25 점수가 2~22 범위일 때
  - 문서 A: dense 0.80 → 1.0, BM25 12 → 0.5 → `0.7×1.0 + 0.3×0.5 = 0.85`
  - 문서 B: dense 0.60 → 0.5, BM25 22 → 1.0 → `0.7×0.5 + 0.3×1.0 = 0.65`
  - A가 B보다 위에 온다.
- 이번 벤치마크에서는 리스트마다 상위 100개를 가져왔다. 꼭 100개일 필요는 없지만, 보여줄 개수보다 넉넉히(상위 10개를 보여준다면 50~100개) 가져와야 한쪽 리스트에만 있는 좋은 문서가 빠지지 않는다.
  - 가져오는 개수가 바뀌면 min-max의 최솟값(리스트의 마지막 문서 점수)도 바뀐다. 그러니 가중치도 실제로 쓸 개수 기준으로 튜닝한다.
- RRF(`1 / (k + 순위)`의 합)는 점수를 버리고 순위만 쓴다. 그래서 두 리스트를 늘 같은 비중으로 섞게 된다.
- Milvus 2.6의 `WeightedRanker`는 min-max가 아니라 고정 함수(BM25는 `2·atan(s)/π`)로 정규화한다. 그래서 min-max를 쓰려면 dense 검색과 BM25 검색을 따로 호출하고 앱에서 합쳐야 한다.

### NFKC 정규화
- 유니코드 정규화 방식 중 하나다. 모양만 다르고 의미가 같은 문자를 표준 형태로 바꾼다.
  - 전각 영문·숫자 → 반각: `ＣｈａｔＧＰＴ１５` → `ChatGPT15`
  - 반각 가타카나 → 전각: `ｱﾌﾟﾘ` → `アプリ`
  - 원문자 숫자 → 숫자: `①` → `1`
- 일본어 텍스트에는 전각 영문이 흔하다. 그대로 두면 어떤 분석기에서도 `ｃｈａｔｇｐｔ`와 `chatgpt`가 다른 토큰이 된다.
- Python에서는 `unicodedata.normalize("NFKC", text)` 한 줄이다. insert와 query 양쪽에서, 텍스트를 Milvus에 넘기기 전에 적용한다.

### 정규화 설정 (analyzer filter)
- `lowercase`: 영문을 소문자로 바꾼다.
- `removepunct`: lindera가 내보내는 공백·구두점 토큰(`' '`, `?`)을 지운다.
- `asciifolding`: 악센트나 전각 라틴 문자를 ASCII로 접는다(`é` → `e`, `ｃ` → `c`).
- `stemmer` (english): 영어 단어를 기본형으로 줄인다(`apps` → `app`, `running` → `run`, `edited` → `edit`). 넣어도 `画像`, `번역` 같은 일본어·한국어 토큰은 그대로라 부작용이 없었다. 필요한 경우는 두 가지다.
  - **같은 분석기 안에서 형태가 다를 때** (더 흔하다): 문서 `photo editing apps`와 쿼리 `photo edit app`은 stemmer가 없으면 `apps / editing`과 `app / edit`으로 갈려 매칭되지 않는다. en 분석기에는 stemmer가 원래 들어 있지만 ja·ko 분석기에는 없다. 그래서 일본어·한국어 문서 속 영어 단어는 이 문제가 그대로 생긴다.
  - **저장과 검색 분석기가 다를 때**: en으로 저장된 `apps`는 `app`이 된다. 그런데 쿼리를 ja로 자르면 `apps` 그대로라 매칭되지 않는다. ja·ko에도 stemmer를 넣으면 양쪽 모두 `app`이 된다.
- **NFKC를 따로 해야 하는 이유**: 필터는 토큰을 자른 뒤에 적용된다. 그런데 토크나이저가 전각 숫자 `１５`를 `1 / 5`로 먼저 쪼개 버린다. 그래서 자르기 전에 앱에서 NFKC로 바꿔 두는 것이 확실하다.

## 벤치마크 구성
- **데이터**: [MIRACL](https://huggingface.co/datasets/mteb/MIRACLRetrievalHardNegatives) dev (ko / ja / en). 사람이 판정한 정답과 hard negative가 들어 있다.
  - KR용: 한국어 문서 43k + 일본어 5k + 영어 2.5k
  - JP용: 일본어 문서 40k + 한국어 5k + 영어 2.5k
- **쿼리 형태**: 원래 질문형(`q`)에 더해, 앱 검색을 흉내 내려고 정규식으로 키워드형(`kw`)과 2단어형(`short`)을 만들었다. 토크나이저로 만들면 특정 토크나이저에 유리해지기 때문에 정규식만 썼다.
  - 예: `森上亜希子の出身はどこ` → `森上亜希子 出身`
  - 예: `룩셈부르크의 수도는 어디인가?` → `룩셈부르크 수도`
- **임베딩**: bge-m3 dense (1024차원), HNSW (M=16, efConstruction=200)
- **비교 구성**
  - `C0`: 기본 언어 토크나이저 하나 (KR은 lindera ko-dic, JP는 lindera ipadic)
  - `C1`: multi analyzer. insert할 때 언어를 감지해 `lang` 필드에 넣고, query할 때는 감지된 언어 하나로 `analyzer_name`을 지정
  - `C2`: `C1` + 애매한 쿼리(한자만 있거나 한글과 가나가 섞인 경우)를 fan-out
- **지표**
  - **nDCG@10**: 상위 10개 결과에 정답 문서가 얼마나 위쪽에 있는지를 0~1로 나타낸 점수다. 높을수록 좋다.
  - **95% 신뢰구간 (paired bootstrap)**: 같은 쿼리에서 C0과의 점수 차이를 구한 뒤, 쿼리를 무작위로 다시 뽑는 시뮬레이션을 1만 번 돌려 차이의 범위를 추정했다.
    - `+0.034 [+0.017, +0.054]`처럼 구간이 0을 포함하지 않으면 실제로 차이가 있는 것이다.
    - `−0.008 [−0.017, +0.000]`처럼 0을 포함하면 차이가 있다고 말할 수 없다.

## 결과 1. multi analyzer

하이브리드(가중합, dense 0.7) 기준 C0 대비 nDCG@10 변화.

| 쿼리 | KR 클러스터 | JP 클러스터 |
|---|---|---|
| 한국어 (질문 / 키워드 / 2단어) | ±0.000 | **+0.018 / +0.034 / +0.020** |
| 일본어 (질문 / 키워드 / 2단어) | −0.012 / −0.008 / −0.008 (질문형만 소폭 유의, 나머지는 유의하지 않음) | +0.001 / 0.000 / 0.000 |
| 영어 (질문 / 키워드 / 2단어) | 차이 없음 | 차이 없음 |

- BM25 단독으로 보면 JP 클러스터 한국어 쿼리 차이가 더 크다(**+0.10 ~ +0.16**). 하이브리드에서는 dense가 일부를 메워서 차이가 줄어든다.
- **비대칭이 생기는 이유**
  - **ko-dic은 일본어를 그럭저럭 처리한다.** 한자어 사전이 있어서 `太陽誘電の創始者` → `太陽 / 誘 / 電 / の / 創始 / 者`처럼 잘게 쪼갠다. 문서와 쿼리를 똑같이 쪼개기 때문에 BM25 매칭은 유지된다.
  - **ipadic은 한글을 처리하지 못한다.** `비행장은`, `제주도민들이`처럼 조사가 붙은 어절이 통째로 토큰이 되어 거의 매칭되지 않는다.
- JP 코퍼스 전체를 ko-dic 하나로 통일해 봐도, 일본어 쿼리가 −0.006 ~ −0.019 떨어졌다. 그래서 JP 클러스터에서는 multi analyzer가 맞는 선택이다.

- 언어 지정 규칙과 그 이유는 위 "핵심 개념과 이유 정리"에 정리했다.
- 일본어+영어 혼합은 직접 측정했다(JP, 쿼리 119개). ja 하나로 처리한 결과가 ipadic 단일과 같았다.
- 한국어+일본어 혼합을 ko로 보내는 규칙은 혼합 텍스트로 직접 잰 결과가 아니다. 각 언어를 따로 잰 결과로 추론한 것이다.

## 결과 2. fan-out은 효과가 없다
- 한자만 있는 키워드 쿼리를 ja/zh로 fan-out해서 RRF로 합치면 **−0.02 ~ −0.07** 떨어졌다. 일본어+영어 쿼리를 ja/en으로 fan-out해도 −0.06이었다.
- **원인**: insert 때와 다른 토크나이저로 자른 쿼리는 엉뚱한 문서와만 일부 겹친다. 그런데 RRF는 점수가 아니라 순위만 보기 때문에, 그 노이즈 결과의 1등이 정상 결과의 1등과 같은 비중을 받는다.
- 문서별로 BM25 점수가 높은 쪽을 고르는 방식(max 병합)으로 합치면 손해는 사라진다. 하지만 이득도 없다.
- **영어 부분이 원래 문제가 되지 않는다.** ko-dic, ipadic, english 분석기 모두 영어를 소문자로 바꾸고 단어 단위로 자른다. insert와 query에 같은 분석기만 쓰면 어느 분석기든 매칭된다.

## 결과 3. RRF보다 가중합

nDCG@10 (C1 기준)

| 방식 | KR | JP |
|---|---|---|
| BM25만 | 0.493 | 0.424 |
| dense(bge-m3)만 | 0.701 | 0.703 |
| RRF (k=60) | 0.661 | 0.619 |
| RRF (k=20) | 0.673 | 0.640 |
| Milvus `WeightedRanker` (dense 0.7, `norm_score=True`) | 0.704 | 0.683 |
| **min-max 정규화 후 가중합 (dense 0.7)** | **0.725** | **0.718** |

- **RRF는 dense만 쓸 때보다 나빴다.** 두 리스트를 같은 비중으로 섞는데, 이 데이터에서는 BM25가 dense보다 훨씬 약하다.
- **Milvus `WeightedRanker`의 정규화가 BM25 점수를 뭉갠다.** `norm_score=True`이면 BM25 점수를 `2·atan(s)/π`로 정규화한다(v2.6). 그러면 BM25 10점은 0.94, 20점은 0.97이 되어 점수 차이가 거의 사라진다.
- 하이브리드가 dense만 쓸 때보다 나았던 건 **앱에서 직접 min-max 정규화한 가중합**뿐이었다(KR +0.024, JP +0.015).
- 가중치 0.7은 이 데이터 기준이다. MIRACL은 위키 질문이라 dense에 유리하다. 앱 이름처럼 고유명사가 많은 검색에서는 BM25 비중을 더 높여야 할 수도 있으니, 실제 검색 로그로 다시 튜닝해야 한다.

## 덤: analyzer 설정에서 챙길 것
- **lindera는 공백과 구두점을 토큰으로 내보낸다.** `removepunct` 필터를 넣자.
- **전각 영문(`ＣｈａｔＧＰＴ`)은 어떤 분석기에서도 `chatgpt`와 매칭되지 않는다.** 앱에서 insert와 query 전에 NFKC 정규화를 하고, `asciifolding`과 영어 `stemmer` 필터(`apps` → `app`)를 추가하자.
  - MIRACL에서는 효과가 +0.001 ~ +0.003으로 미미했지만 손해도 없었다. 위키피디아에는 전각 영문이 드물기 때문이다. 앱 데이터에서는 효과가 더 클 수 있다.

```json
{
  "tokenizer": {"type": "lindera", "dict_kind": "ipadic"},
  "filter": ["lowercase", "removepunct", "asciifolding",
             {"type": "stemmer", "language": "english"}]
}
```

- 컬렉션에 데이터를 넣자마자 벤치마크를 돌리면 인덱스가 아직 다 만들어지지 않은 상태에서 검색된다. 실제로 처음 잰 수치가 그래서 틀어졌다. `describe_index`의 `indexed_rows`가 전체 행 수와 같아질 때까지 기다린 뒤 측정하자.

## 한계
- **bge-m3는 학습 데이터에 MIRACL train 셋이 들어 있다.** 평가에 쓴 dev 쿼리와는 다르지만 같은 출처라서 dense 점수가 실제보다 좋게 나왔을 수 있다. 그래서 "dense가 BM25보다 훨씬 강하다"는 결과와 가중치 0.7은 실제 데이터에서 BM25 쪽으로 바뀔 수 있다.
- MIRACL은 위키피디아 데이터다. 키워드 쿼리도 정규식으로 만든 합성 데이터라서 실제 앱 이름·설명 데이터와는 분포가 다르다.
- 한국어+일본어, 한국어+영어가 섞인 쿼리는 데이터셋에 거의 없어서 직접 측정하지 못했다.
- 중국어 문서가 의미 있게 들어오는 환경이라면 ja/zh fan-out 결론이 달라질 수 있다.
- 결론을 확정하려면 실제 앱 카탈로그와 검색 로그 일부로 같은 비교를 돌려 보는 것이 가장 확실하다.
