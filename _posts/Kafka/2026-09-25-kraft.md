## 들어가며
- Kafka 4.0부터 ZooKeeper가 완전히 제거되고 KRaft만 남았다. KRaft가 무엇인지 소스 코드 레벨에서 확인해 보고, 현시점(2026-09) 버전 선택과 업그레이드 경로를 핵심만 정리한 포스팅
- 코드 인용은 추천 버전인 `apache/kafka` **4.2.1** 태그 기준

## KRaft란?
- **K**afka + **Raft**. 클러스터 메타데이터(브로커 목록, 토픽/파티션, 리더/ISR, 설정, ACL 등)를 ZooKeeper가 아닌 **Kafka 자체의 Raft 합의 로그**로 관리하는 방식이다. (KIP-500)

### ZooKeeper 시절의 문제
- 메타데이터 원본은 ZooKeeper, 그걸 읽어서 판단하는 건 브로커 중 하나인 **컨트롤러**. 저장소와 두뇌가 분리되어 있었다.
- 컨트롤러가 죽으면 새 컨트롤러가 **ZK에서 전체 메타데이터를 다시 읽어야** 했다. 파티션이 많을수록 페일오버가 느려지고, 이게 파티션 수의 실질적인 상한이 됐다.
- 컨트롤러가 브로커들에게 메타데이터를 push(RPC)하는 구조라 브로커 간 메타데이터 불일치가 생길 수 있었다.
- 운영 측면에서도 ZK라는 별도 분산 시스템을 따로 배포·모니터링·보안 설정해야 했다.

### KRaft의 구조
```
      ┌──────────── Controller Quorum (3 or 5대) ────────────┐
      │  Active Controller (Raft Leader)   Standby   Standby │
      │        │  __cluster_metadata 로그를 Raft로 복제      │
      └────────┼─────────────────────────────────────────────┘
               │  Fetch (pull)
     ┌─────────┼──────────┐
   Broker    Broker     Broker     ← observer: 로그를 따라 읽어서 메모리에 반영
```
- 메타데이터는 `__cluster_metadata`라는 **단일 파티션 내부 토픽**에 이벤트 로그로 쌓인다.
  ```java
  // clients/.../common/internals/Topic.java
  public static final String CLUSTER_METADATA_TOPIC_NAME = "__cluster_metadata";
  ```
- 컨트롤러 노드들(voter)이 Raft로 이 로그를 복제하고, **Raft 리더 = Active Controller** 가 된다. 나머지는 로그를 계속 재생(replay)하며 대기하는 hot standby.
  > "The node which is the leader of the metadata log becomes the active controller. All other nodes remain in standby mode. ... They just replay the metadata log entries that the current active controller has created." — `QuorumController.java`
- 브로커는 투표권이 없는 **observer**로, 같은 로그를 fetch해서 자기 메모리에 반영한다.
- 결과적으로
  - **페일오버가 빠르다**: standby가 이미 최신 상태를 메모리에 들고 있어서 "다시 읽기"가 필요 없다.
  - **확장성**: 파티션 수 상한이 크게 올라간다.
  - **일관성**: 모두가 같은 로그의 offset을 기준으로 메타데이터를 맞춘다.
  - **운영 단순화**: Kafka 하나만 운영하면 된다.

## 코드로 보는 KRaft 동작 원리
- 핵심 클래스는 `raft` 모듈의 `KafkaRaftClient`(합의)와 `metadata` 모듈의 `QuorumController`(메타데이터 처리)다.

### 1. "Kafka스러운" Raft - push가 아니라 pull
```java
/**
 * This class implements a Kafkaesque version of the Raft protocol. Leader election
 * is more or less pure Raft, but replication is driven by replica fetching ...
 */
public final class KafkaRaftClient<T> implements RaftClient<T> {
```
- 교과서 Raft는 리더가 `AppendEntries`로 팔로워에게 **push**한다. KRaft는 선출만 Raft 그대로이고, 복제는 기존 Kafka 파티션 복제처럼 팔로워가 **Fetch로 pull**한다.
- 그래서 Raft에 없는 API가 생긴다. pull 구조에서는 팔로워가 새 리더를 알 방법이 없으므로, 리더가 당선 직후 `BeginQuorumEpoch`를 보내 "내가 이번 epoch의 리더"라고 알린다.
- 사용하는 RPC: `Vote`, `BeginQuorumEpoch`, `EndQuorumEpoch`(정상 종료 시 사임), `Fetch`, `FetchSnapshot`

### 2. 리더 선출 - 상태 머신
- `QuorumState.java` 주석에 상태 전이가 정리되어 있다.
```
Unattached ──(election timeout)──▶ Prospective ──(PreVote 과반)──▶ Candidate ──(Vote 과반)──▶ Leader
     ▲                                                                                         │
     └──────────── 더 높은 epoch 발견 ──────────── Follower ◀────── 더 높은 epoch의 리더 발견 ──┘
```
- **Prospective(PreVote)**: 바로 epoch을 올리며 선거를 시작하지 않고, 먼저 "나 뽑힐 수 있을까?"를 물어본다. 네트워크가 잠깐 끊겼던 노드가 복귀하면서 불필요하게 epoch을 올려 멀쩡한 리더를 끌어내리는 걸 막는다. (KIP-996)
- **투표 조건**: 후보의 로그가 내 로그보다 최소한 같거나 더 최신일 때만 표를 준다.
  ```java
  // KafkaRaftClient.java
  lastEpochEndOffsetAndEpoch.compareTo(endOffset()) >= 0
  ```
  → 커밋된 데이터를 갖지 못한 노드는 리더가 될 수 없다.
- **Observer(브로커)** 는 `Unattached ↔ Follower`만 오간다. 선거에는 참여하지 않는다.

### 3. 커밋(High Watermark) - 과반이 받아간 지점
```java
// LeaderState.java
private boolean maybeUpdateHighWatermark() {
    // Find the largest offset which is replicated to a majority of replicas (the leader counts)
    ... followersByDescendingFetchOffset() ...
    int indexOfHw = voterStates.size() / 2;
```
- voter들의 fetch offset을 내림차순 정렬한 뒤 **가운데(과반) 위치**의 offset이 HW, 즉 커밋 지점이 된다. voter 3대면 index 1 → 2대 이상이 가져간 offset이다.
- 추가 조건: `highWatermarkUpdateOffset > epochStartOffset`. **새 리더는 자기 epoch에서 쓴 레코드가 하나 커밋되기 전까지 HW를 올리지 않는다.** (Raft 논문의 "이전 term 엔트리는 현재 term 엔트리를 통해서만 커밋" 규칙)
- 리더도 스스로를 감시한다(check quorum). 일정 시간 과반 voter로부터 fetch가 안 오면 네트워크에서 고립된 것으로 보고 리더 자리를 내려놓는다.
  ```java
  "Did not receive fetch request from the majority of the voters within {}ms. "
  ```

### 4. Active Controller - 단일 스레드 + 로그 선기록
> "The QuorumController is single-threaded. A single event handler thread performs most operations. ... The future associated with each operation will not be completed until the results of the operation have been made durable to the metadata log."
- 토픽 생성 같은 요청은 단일 이벤트 스레드에서 처리한다. 락이 필요 없다.
- 결과를 레코드(`TopicRecord`, `PartitionRecord` ...)로 만들어 메타데이터 로그에 append하고, **커밋(과반 복제)된 뒤에야** 클라이언트에 응답한다.

### 5. 브로커 쪽 - 로그를 이미지로
- 브로커의 `MetadataLoader`가 `RaftClient.Listener`로 커밋된 레코드를 받아 **delta → image(불변 스냅샷 객체)** 로 만든다. `BrokerMetadataPublisher`, `KRaftMetadataCachePublisher`(`core/.../server/metadata`) 같은 publisher가 이 image를 실제 메타데이터 캐시와 파티션 상태에 반영한다.
- 즉 브로커의 메타데이터 = `__cluster_metadata` 로그를 어느 offset까지 읽었는가. 브로커 간 불일치는 "offset 차이"로만 존재하고, 결국 같은 상태로 수렴한다.

### 6. 스냅샷 - 로그가 무한히 커지지 않게
- 로그를 계속 재생하면 시작이 느려지므로 주기적으로 스냅샷을 찍고 앞부분 로그를 정리한다. 설정 기본값은 **마지막 스냅샷 이후 20MB 또는 1시간** 중 먼저 도달하는 쪽이다. (`MetadataLogConfig.java`)
  - `metadata.log.max.record.bytes.between.snapshots`
  - `metadata.log.max.snapshot.interval.ms`
- 너무 뒤처진 팔로워가 요청한 offset이 리더의 log start offset보다 앞이면, Fetch 응답으로 스냅샷 ID를 받아 `FetchSnapshot`으로 스냅샷부터 받아간다.

### 운영 관점 핵심 설정
```properties
process.roles=controller            # broker | controller | broker,controller(combined: 개발용)
node.id=3000
controller.listener.names=CONTROLLER
controller.quorum.bootstrap.servers=c1:9093,c2:9093,c3:9093   # 동적 쿼럼(3.9+, KIP-853)
# controller.quorum.voters=3000@c1:9093,...                   # 정적 쿼럼(기존 방식)
```
- 컨트롤러는 **3대(1대 장애 허용) 또는 5대(2대 장애 허용)**. 과반이 살아 있어야 메타데이터를 쓸 수 있다.
- `metadata.version`은 메타데이터 레코드 포맷 버전(feature flag)이다. `kafka-features.sh`로 올리고, 올린 뒤에는 되돌릴 수 없다고 보는 게 안전하다.

## 결론 1. 현시점 추천 버전 조합
- **Kafka 4.2.x + Kafka Connect 4.2.x (같은 버전)**, Java 17+(21 LTS 권장), KRaft
  - 지원 중인 라인은 4.3.x / 4.2.x / 4.1.x 세 개. 4.2는 충분히 성숙했고 지원 기간도 남아 있다.
  - 작성 시점에 `4.2.2-rc1`이 투표 중이다. 릴리즈되면 4.2.2로 올리자.
  - 최신 기능이 필요한 신규 구축이면 4.3.1도 괜찮다. (`4.4.0-rc1`도 투표 중)
- Connect는 Kafka 배포판에 포함되어 있으므로 브로커와 버전을 맞추는 게 가장 안전하다. 업그레이드 순서는 **브로커 먼저, Connect 나중**.
- 커넥터 플러그인(Debezium 등)이 Kafka 4.x 클라이언트를 지원하는지 꼭 확인한다. 4.0에서 2.1 미만 클라이언트 프로토콜이 제거됐다.

## 결론 2. 3.x → 4.x 업그레이드 경로
| 현재 | 경로 |
|---|---|
| 3.x ZooKeeper 모드 | 3.9.x로 업그레이드 → KRaft 마이그레이션 → 4.2.x |
| 3.3+ KRaft | 4.2.x로 바로 롤링 업그레이드 |
| 3.3 미만 KRaft | 3.3+ 경유 후 4.x |

- **ZK 모드는 4.x로 바로 못 간다.** 4.x 바이너리에는 ZK 모드도 마이그레이션 기능도 없기 때문이다.
- ZK → KRaft 마이그레이션 흐름 (3.9.x에서)
  1. 3.9.x로 롤링 업그레이드, `inter.broker.protocol.version=3.9`
  2. KRaft 컨트롤러 쿼럼 신규 구성 (**기존 ZK 클러스터 ID로 포맷**, `zookeeper.metadata.migration.enable=true`)
  3. 브로커를 마이그레이션 모드로 롤링 재시작 → 메타데이터가 ZK에서 KRaft로 복사됨
  4. 브로커를 KRaft 모드로 롤링 재시작 (듀얼 라이트 유지, **아직 롤백 가능**)
  5. 컨트롤러에서 ZK 설정 제거 = **Finalize (이후 롤백 불가)** → ZK 폐기
  6. 4.2.x로 롤링 업그레이드 (컨트롤러 → 브로커) 후 `metadata.version` 상향

## 결론 3. 왜 "3.3 미만 KRaft"는 바로 못 가나?
- 4.x가 읽을 수 있는 최소 `metadata.version`이 **3.3-IV3**이기 때문이다. 3.3 미만 KRaft의 메타데이터 포맷은 4.x가 이해하지 못한다.
  ```java
  // server-common/.../MetadataVersion.java
  public static final MetadataVersion MINIMUM_VERSION = IBP_3_3_IV3;
  ```
- `QuorumController` 주석에도 "Starting with 3.3, this version must be set before the controller can fully initialize."라고 되어 있다. 3.3이 `metadata.version` 체계가 확립되고 KRaft가 production-ready가 된 기준점이다.
